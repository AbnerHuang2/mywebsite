前言

“Premature optimization is the root of all evil” — Donald Knuth

在开始优化代码之前，我们必须先知道如何测量性能。本章将详细介绍Go语言的基准测试工具和最佳实践。

1. 基准测试的基本规则

在开始编写基准测试之前，你需要有一个安静稳定的环境来运行测试。

不要在共享硬件上运行基准测试

不要在共享硬件上运行基准测试，不要在运行基准测试时浏览网页或播放音乐。

建议：

  • 关闭所有不必要的程序
  • 禁用任何自动更新和后台服务
  • 确保机器负载低

多次运行基准测试

如果你的环境出现噪音，可以增加运行时间来减少噪音的影响：

go test -bench=. -benchtime=10s

注意功耗管理和热伸缩（thermal scaling）

现代处理器会根据温度和功耗动态调整频率。在运行基准测试时：

  • 确保机器已经"预热"
  • 笔记本电脑应该插电源运行
  • 考虑禁用CPU频率缩放（Linux）

Linux示例：禁用频率缩放

# 查看当前频率governor
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

# 设置为性能模式
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

注意虚拟化和云基础设施

虚拟机和云实例可能：

  • 与其他租户共享CPU
  • 网络和磁盘I/O可能不稳定
  • 可能有noisy neighbor问题

建议： 在性能测试时使用裸机或专用实例。

2. 使用testing包进行基准测试

Go的testing包内置了基准测试支持。

2.1 第一个基准测试 

// fib.go
package fib

func Fib(n int) int {
    if n < 2 {
        return n
    }
    return Fib(n-1) + Fib(n-2)
}

// fib_test.go
package fib

import "testing"

func BenchmarkFib10(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Fib(10)
    }
}

关键点：

  • 基准测试函数必须以Benchmark开头
  • 接受一个*testing.B参数
  • 循环执行b.N次——由测试框架自动调整

2.2 运行基准测试 

# 运行当前目录的所有基准测试
go test -bench=.

# 运行匹配特定模式的基准测试
go test -bench=Fib

# 只运行基准测试，跳过单元测试
go test -run=^$ -bench=.

输出示例：

goos: darwin
goarch: amd64
pkg: github.com/davecheney/high-performance-go-workshop/examples/fib
BenchmarkFib10-8         5000000    338 ns/op
PASS
ok      github.com/davecheney/high-performance-go-workshop/examples/fib    2.038s

输出解读：

  • BenchmarkFib10-8：基准测试名称，8是GOMAXPROCS
  • 5000000：运行了500万次迭代
  • 338 ns/op：每次操作平均耗时338纳秒

2.3 benchtime标志

默认情况下，基准测试运行1秒。如果基准测试在1秒内完成，b.N会增加，测试会再次运行。

# 运行更长时间以提高准确性
go test -bench=. -benchtime=3s

# 指定固定的迭代次数
go test -bench=. -benchtime=50x

示例： 测试不同的benchtime

go test -bench=Fib1 -benchtime=1s
# BenchmarkFib1-8   1000000000   2.05 ns/op

go test -bench=Fib1 -benchtime=3s  
# BenchmarkFib1-8   3000000000   2.06 ns/op

go test -bench=Fib1 -benchtime=10s
# BenchmarkFib1-8   10000000000  2.05 ns/op

2.4 提高基准测试准确性

基准测试结果的准确性由这几个因素决定：

  • 运行时间越长越准确
  • 迭代次数越多越准确
  • 环境越稳定越准确

建议的benchtime：

  • 快速测试：1-3秒（默认）
  • 准确测试：5-10秒
  • 非常准确：30秒以上

3. 使用benchstat比较基准测试

基准测试结果会有变化，单次运行不可靠。benchstat工具可以进行统计分析。

3.1 安装benchstat 

go install golang.org/x/perf/cmd/benchstat@latest

3.2 使用benchstat

步骤1： 运行基准测试多次并保存结果

# 优化前
go test -bench=. -count=10 > old.txt

# 修改代码进行优化...

# 优化后
go test -bench=. -count=10 > new.txt

步骤2： 使用benchstat比较

benchstat old.txt new.txt

输出示例：

name     old time/op  new time/op  delta
Fib10-8   338ns ± 2%   170ns ± 1%  -49.70%  (p=0.000 n=10+10)

输出解读：

  • ±2%：标准差（性能变化范围）
  • -49.70%：性能提升了49.7%
  • (p=0.000 n=10+10)：p值，接近0表示差异显著

3.3 理解p值

p值（p-value） 表示差异的统计显著性：

  • p < 0.05：差异显著（95%置信度）
  • p < 0.01：差异非常显著（99%置信度）
  • p > 0.05：差异可能是噪音，不显著

示例：

name     old time/op  new time/op  delta
Fib10-8   338ns ± 2%   170ns ± 1%  -49.70%  (p=0.000 n=10+10)  // 显著
Fib10-8   338ns ± 5%   335ns ± 6%   -0.89%  (p=0.234 n=10+10)  // 不显著

4. 避免基准测试的启动成本

4.1 问题：包含初始化时间 

// ❌ 错误：每次迭代都重新创建数据
func BenchmarkBad(b *testing.B) {
    for i := 0; i < b.N; i++ {
        // 每次都创建，初始化成本被计入
        data := make([]int, 10000)
        for j := range data {
            data[j] = j
        }
        // 实际要测试的函数
        processData(data)
    }
}

4.2 解决方案：使用b.ResetTimer() 

// ✅ 正确：排除初始化成本
func BenchmarkGood(b *testing.B) {
    // 在循环外准备数据
    data := make([]int, 10000)
    for j := range data {
        data[j] = j
    }
    
    // 重置计时器，排除准备时间
    b.ResetTimer()
    
    for i := 0; i < b.N; i++ {
        processData(data)
    }
}

4.3 使用b.StopTimer()和b.StartTimer()

如果需要在循环内进行准备工作：

func BenchmarkComplexSetup(b *testing.B) {
    for i := 0; i < b.N; i++ {
        b.StopTimer()  // 停止计时
        data := generateTestData()  // 不计入的准备工作
        b.StartTimer()  // 重新开始计时
        
        processData(data)  // 实际测试的代码
    }
}

注意： 过度使用StopTimer/StartTimer会影响基准测试的准确性。尽量在循环外准备数据。

5. 测量内存分配

5.1 为什么关注内存分配？

内存分配的代价：

  1. 分配本身需要时间 - 向操作系统申请内存
  2. 增加GC压力 - 更多分配意味着更频繁的GC
  3. 影响缓存性能 - 堆分配的数据可能不在缓存中

5.2 启用内存统计

使用-benchmem标志：

go test -bench=. -benchmem

5.3 示例：预分配的影响 

// 方法1：不预分配
func AppendWithoutPrealloc(n int) []int {
    var result []int
    for i := 0; i < n; i++ {
        result = append(result, i)
    }
    return result
}

// 方法2：预分配
func AppendWithPrealloc(n int) []int {
    result := make([]int, 0, n)
    for i := 0; i < n; i++ {
        result = append(result, i)
    }
    return result
}

func BenchmarkAppendWithoutPrealloc(b *testing.B) {
    for i := 0; i < b.N; i++ {
        AppendWithoutPrealloc(1000)
    }
}

func BenchmarkAppendWithPrealloc(b *testing.B) {
    for i := 0; i < b.N; i++ {
        AppendWithPrealloc(1000)
    }
}

运行结果：

$ go test -bench=Append -benchmem
BenchmarkAppendWithoutPrealloc-8   50000   32420 ns/op   57344 B/op   11 allocs/op
BenchmarkAppendWithPrealloc-8     100000   16580 ns/op    8192 B/op    1 allocs/op

结果分析：

  • 时间： 预分配快了95%（16580 vs 32420 ns）
  • 内存： 预分配少用了86%的内存（8192 vs 57344 B）
  • 分配次数： 从11次减少到1次

输出字段解释：

  • 32420 ns/op：每次操作耗时
  • 57344 B/op：每次操作分配的字节数
  • 11 allocs/op：每次操作的分配次数

6. 注意编译器优化

6.1 问题：编译器可能优化掉代码

Go编译器非常聪明，如果它发现计算结果没有被使用，可能会完全优化掉你的代码。

// ❌ 问题：result没有被使用
func BenchmarkFibWrong(b *testing.B) {
    for i := 0; i < b.N; i++ {
        Fib(10)  // 编译器可能优化掉这个调用
    }
}

6.2 解决方案1：使用包级变量 

var result int  // 包级变量

func BenchmarkFibCorrect(b *testing.B) {
    var r int
    for i := 0; i < b.N; i++ {
        r = Fib(10)
    }
    result = r  // 赋值给包级变量，防止优化
}

6.3 解决方案2：使用testing.B的字段

Go 1.13+，更推荐的方式：

func BenchmarkFibBetter(b *testing.B) {
    var r int
    for i := 0; i < b.N; i++ {
        r = Fib(10)
    }
    // 将结果存储在b的字段中（虽然b没有这个字段，但编译器会防止优化）
    _ = r
}

6.4 对于多返回值 

func Search(slice []int, target int) (int, bool) {
    // ...
}

var (
    index int
    found bool
)

func BenchmarkSearch(b *testing.B) {
    data := generateData()
    var idx int
    var fnd bool
    b.ResetTimer()
    
    for i := 0; i < b.N; i++ {
        idx, fnd = Search(data, 42)
    }
    
    index = idx
    found = fnd
}

7. 常见的基准测试错误

7.1 错误1：测试环境不稳定 

// ❌ 问题：在吵闹的环境中运行
// - 浏览器打开
// - 音乐播放器运行
// - 后台更新进行中
// - CPU频率动态变化

// ✅ 解决方案：
// - 关闭不必要的程序
// - 固定CPU频率
// - 使用-count增加采样
go test -bench=. -count=20

7.2 错误2：只运行一次 

// ❌ 单次运行不可靠
go test -bench=.

// ✅ 多次运行，使用benchstat
go test -bench=. -count=10 > result.txt
benchstat result.txt

7.3 错误3：忽略内存分配 

// ❌ 只看时间
go test -bench=.

// ✅ 同时看时间和内存
go test -bench=. -benchmem

内存分配往往是性能瓶颈的根源。

7.4 错误4：基准测试太简单 

// ❌ 问题：测试的代码太简单，可能被内联优化
func BenchmarkTooSimple(b *testing.B) {
    for i := 0; i < b.N; i++ {
        x := i + 1  // 这可能被完全优化掉
    }
}

// ✅ 测试真实的使用场景
func BenchmarkRealistic(b *testing.B) {
    data := generateRealData()
    b.ResetTimer()
    
    for i := 0; i < b.N; i++ {
        result := processData(data)
        doSomethingWith(result)
    }
}

8. 从基准测试中进行性能剖析

你可以直接从基准测试生成性能剖析数据。

8.1 生成CPU profile 

go test -bench=. -cpuprofile=cpu.prof

8.2 生成内存profile 

go test -bench=. -memprofile=mem.prof

8.3 分析profile 

# 分析CPU profile
go tool pprof cpu.prof

# 分析内存profile
go tool pprof mem.prof

pprof命令：

(pprof) top
(pprof) list functionName
(pprof) web

9. 实战示例：字符串拼接

9.1 场景

比较三种字符串拼接方法的性能。

package concat

import (
    "strings"
    "testing"
)

var testStrings = []string{
    "hello", "world", "this", "is", "a", "test",
}

// 方法1：使用+操作符
func ConcatPlus(strs []string) string {
    result := ""
    for _, s := range strs {
        result += s
    }
    return result
}

// 方法2：使用strings.Builder
func ConcatBuilder(strs []string) string {
    var builder strings.Builder
    for _, s := range strs {
        builder.WriteString(s)
    }
    return builder.String()
}

// 方法3：预分配容量的Builder
func ConcatBuilderPrealloc(strs []string) string {
    totalLen := 0
    for _, s := range strs {
        totalLen += len(s)
    }
    
    var builder strings.Builder
    builder.Grow(totalLen)  // 预分配
    for _, s := range strs {
        builder.WriteString(s)
    }
    return builder.String()
}

var result string

func BenchmarkConcatPlus(b *testing.B) {
    var r string
    for i := 0; i < b.N; i++ {
        r = ConcatPlus(testStrings)
    }
    result = r
}

func BenchmarkConcatBuilder(b *testing.B) {
    var r string
    for i := 0; i < b.N; i++ {
        r = ConcatBuilder(testStrings)
    }
    result = r
}

func BenchmarkConcatBuilderPrealloc(b *testing.B) {
    var r string
    for i := 0; i < b.N; i++ {
        r = ConcatBuilderPrealloc(testStrings)
    }
    result = r
}

9.2 运行对比 

$ go test -bench=Concat -benchmem -count=10 > result.txt
$ benchstat result.txt

结果：

name                         time/op
ConcatPlus-8                 1.20µs ± 3%
ConcatBuilder-8              0.45µs ± 2%
ConcatBuilderPrealloc-8      0.28µs ± 1%

name                         alloc/op
ConcatPlus-8                  312B ± 0%
ConcatBuilder-8               216B ± 0%
ConcatBuilderPrealloc-8       64B ± 0%

name                         allocs/op
ConcatPlus-8                  5.00 ± 0%
ConcatBuilder-8               4.00 ± 0%
ConcatBuilderPrealloc-8       1.00 ± 0%

分析：

  1. strings.Builder比+操作符快62.5%
  2. 预分配的Builder比+操作符快76.7%
  3. 预分配的Builder内存分配减少了79.5%
  4. 预分配的Builder分配次数从5次减少到1次

10. 讨论：基准测试的局限性

10.1 微基准测试 vs 宏基准测试

微基准测试（Micro-benchmarks）：

  • 测试单个函数或小段代码
  • 容易编写和运行
  • 可能不代表真实使用场景
  • 编译器优化可能与实际不同

宏基准测试（Macro-benchmarks）：

  • 测试整个应用或请求流程
  • 更接近真实场景
  • 更难设置和维护
  • 结果更有实际意义

建议： 两者结合使用。

10.2 基准测试不能替代生产监控

基准测试：

  • ✅ 帮助你理解代码性能
  • ✅ 比较不同实现
  • ✅ 防止性能退化

但不能：

  • ❌ 预测真实负载下的行为
  • ❌ 发现所有瓶颈
  • ❌ 替代生产环境监控

建议： 基准测试 + 生产监控 + 压力测试

10.3 不要过早优化

“Premature optimization is the root of all evil” — Donald Knuth

正确的流程：

  1. 写出正确的代码
  2. 测量性能
  3. 如果性能不够，找到瓶颈
  4. 优化瓶颈
  5. 再次测量验证
  6. 重复3-5

不要：

  • ❌ 在没有测量的情况下优化
  • ❌ 优化不重要的代码
  • ❌ 为了性能牺牲可读性（除非必要）

11. 总结

核心要点

  1. 稳定的测试环境 - 关闭不必要的程序，固定CPU频率
  2. 多次运行 - 使用-count和benchstat进行统计分析
  3. 排除启动成本 - 使用b.ResetTimer()
  4. 测量内存分配 - 使用-benchmem标志
  5. 防止编译器优化 - 将结果赋值给包级变量
  6. 避免常见错误 - 不稳定环境、单次运行、忽略内存

基准测试检查清单

  • 测试环境稳定（关闭后台程序）
  • 使用b.ResetTimer()排除准备时间
  • 运行足够长时间（-benchtime=3s）
  • 多次运行（-count=10）
  • 使用benchstat比较结果
  • 测量内存分配（-benchmem）
  • 防止编译器优化掉测试代码
  • 测试真实的使用场景
